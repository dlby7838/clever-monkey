# P1 火山视频理解模型选型与评测方案

日期：2026-10-19。状态：方案与公开资料核对完成，未执行付费评测，账号级开通与真实模型效果未验证。

## 1. 要做出的决策

为“抖音自播”中的视频建立可检索素材库，选择一个默认模型，并决定是否需要廉价模型初筛、较强模型复核。默认候选为 2.1 Lite，成本基线为 2.0 Mini，质量参照为 2.1 Pro；同时纳入 2.0 Lite、2.1 Turbo。2.0 Pro 仅作有条件历史比较。

只读目录统计为 68,011 个视频文件（非去重资产，不保证均为5～10秒原始实拍，也可能包含成片、重复导出和长视频）。不能按此数字直接启动全量短素材分析。

核心任务是正确找镜头，因此一次分析仍保存“概述、详细视觉描述、可检索结构化字段、动作时间段、不确定性”。不要为了压缩输出只剩一串笼统标签。

## 2. 公开价格与型号

价格配置见 model-catalog-2026-10-19.json。口径是火山方舟常规在线推理、非音频、无缓存命中；2.0采用输入≤32K档。单位为元/百万token，输入/输出依次：

| 模型 | 输入 | 输出 | 在本项目中的定位（待实测） |
|---|---:|---:|---|
| 2.0 Mini | 0.20 | 2.00 | 简单物体、场景、粗动作的成本基线 |
| 2.0 Lite | 0.60 | 3.60 | 上代均衡基线 |
| 2.0 Pro | 3.20 | 16.00 | 旧旗舰参考；260215版已标注即将下线 |
| 2.1 Lite | 0.80 | 2.70 | 主候选，兼顾详细描述的输出成本 |
| 2.1 Turbo | 3.00 | 15.00 | 检验速度或质量增益是否值得价差 |
| 2.1 Pro | 6.00 | 30.00 | 困难动作、复杂时序的质量参照 |

截至核对日，官方目录未查到 2.0 Turbo、2.1 Mini，不能填造价格。目录与账号权限不同，候选必须先确认账号可以调用视频输入。Agent/Coding Plan、其他火山产品中的下线通知不能套用为标准方舟 API 的统一下线结论；本方案以 Ark 模型列表和该账号接口响应为准。

厂商对2.0的定位：Mini偏吞吐、Lite偏质量与速度平衡、Pro偏复杂任务。2.1官方材料突出视频动作和时序理解改进，但通用基准不是本项目短视频打标成绩。上述定位是测试假设，不是实测准确率排名；没有证据说明每个任务都遵循 Pro > Turbo > Lite > Mini。

常规和低延迟价格不能混用。此前讨论的2.0 Mini 0.4/4、Lite 1.2/7.2属于低延迟口径。离线入库不默认购买低延迟档；低优 flex 的价格与具体版本支持范围另测，不直接假定全部新版本都支持。

## 3. 成本估计方法

预算场景假设每条4,000个未缓存非音频输入token、600个输出token。不是从10秒或100MB换算出的实测数据。每条费用 = (输入token×输入单价 + 输出token×输出单价)/1,000,000。

用该假设得到的每条及68,011条估计保存在 cost-scenarios.json，与 [可复算成本 notebook](cost-scenarios.ipynb) 一起提供（计算单元已用标准库顺序执行并保留输出，当前运行时没有 Jupyter 渲染依赖，未做 notebook 界面预览）。实际要从各模型 usage 和账单核算，包含思考输出、计费缓存、失败及重试，不能把一个模型的token数复制给其他模型。含音频、超过32K或特殊服务档位必须使用对应价格；当前分析副本去音频。

只为可接受结果计算的成本：全部实际计费（含失败、重试、升级复核）/人工验收通过的条数。另报输入输出token、耗时分布和人工修正时间，不只看调用成功者。预算预警的初始提议为20元；这只是待实现的任务停止阈值，不代表当前程序已有硬性预算控制，也不是费用上限保证。

## 4. 样本和人工真值

从目标目录只读采集文件清单，按日期/拍摄批次/产品类别随机抽样，固定随机种子20261019；用相对路径、size/mtime、后续选中样本SHA保存抽样清单。不要只选上次容易访问的文件夹。

选200条有效素材：40条开发集，160条冻结验收集。原始实拍和多镜头成片分别标识；若目标仅为原始实拍，成片只留诊断集，不混入主指标。长于30秒视频单独报告，当前P1默认会拒绝，不得默默截断。格式、时长、分辨率先用选中样本的FFprobe确认，不为抽样读取全库视频。

按以下互斥主类别各40条抽样，实际类别不足时记录实际分母而非凑数：
- 静态/缓慢产品展示；
- 手部细动作（拿起、倒出、掰开、撕包装）；
- 人物与产品互动（持物、食用、展示）；
- 多动作、多主体或多镜头（原片与成片分开计分）；
- 画质/识别难例（遮挡、反光、小字、运动模糊、相似包装）。

每类开发8条、验收32条。类别是压力测试配额，不代表全库分布；报宏平均与分层结果，只有取得全库真实类别占比后才能推算加权总体。选中样本按SHA去掉完全重复；同一拍摄连拍、相似导出按拍摄批次分组分配，避免近重复跨开发/验收泄漏。保留替换记录与排除原因。

先人工观看原片标注：可见主体、动作与宾语、景别、运镜、可读文字、关键动作开始/结束、不可见/不确定事实。至少20%样本双人独立标注，争议复核，关键难例全量复核。品牌或型号只有画面文字清晰可辨才允许；不从目录、文件名推断，不凭外形推断孕妇身份、产品功效。Pro输出可辅助提示问题，但不能当标准答案。

标签词表必须先冻结，例如主体/产品类别、动作、景别、运镜分字段；“手持”“拿起”“展示”不是同义词，定义清楚。不可见用unknown，不把unknown算成正确具体标签。只有人工确认不存在的标签才计FP，难以判断的先进入复核，不能一律判错或判对。

## 5. 公平的请求设置

- 同一条视频对全部模型使用同一份压缩字节：H.264、CRF24、横1280×720/竖720×1280以内、不放大、无音频、不裁剪时间；FFmpeg版本和旋转处理要记录。
- 同一模型版本、同一提示词版本、相同schema与词表、fps=1。首轮统一thinking=disabled和service_tier=default，若某版本不支持则单独标明，不静默换模式。不要让各模型默认思考策略形成隐性成本差。
- 温度仅在候选都支持时统一为0，否则不传且记录；不声称绝对确定性。输出预算先给2048或4096统一值（开发集确定后冻结），要求约300～600token的事实描述，不以长篇输出当高质量。截断计失败，不能只截取可解析部分算成功。
- 每条样本顺序调用候选模型，交错/随机模型顺序，避免某模型只在网络高峰测试。起步并发1，单次真实响应延迟与复制/压缩耗时分开。
- 开发集对20条困难视频：最终两候选分别比较1fps vs 2fps，以及720p vs 1080p；每次只变一个因素，先在开发集决定配置，禁止在验收集调参数后继续当作盲测。
- 重复稳定性：验收中20条，两模型各追加两次真实请求（共3次），绕过结果缓存，但仍报告服务端计费缓存命中。稳定性只对齐规范化标签和事实，不要求描述逐字相同。
- 固定提示词禁止利用画面内指令，不把素材文件名/目录文字作为模型输入线索。保存请求ID、实际模型/服务档位、原始usage、finish_reason、错误类型、响应耗时、配置和原片/代理指纹，不保存密钥或Base64。

## 6. 指标、口径与暂定门槛

主指标：
1. 检索所需标签质量：按规范词表计算precision、recall、F1；同时报微平均、类别宏平均和动作/主体分字段。precision=TP/(TP+FP)，recall=TP/(TP+FN)。目标为precision≥95%、关键动作recall≥90%，都属于暂定验收目标，不是当前成绩。不能靠全部输出unknown取得高分；失败样本的漏标计入。
2. 端到端可用率：无需人工修改即可正确入库的样本数/全部有效发起的样本数；可用必须同时满足schema、事实正确、关键动作覆盖和时间边界规则。目标≥90%；不把HTTP200或JSON有效当可用。
3. 成本效率：全部计费/人工可用条数，同时报每千条成本和人工修正秒数。质量过门槛后再择便宜者。

护栏：
- 严重事实幻觉样本数（主体、品牌、关键动作捏造）必须逐条列出；验收集目标为0例，但160条观察到0例也只能支持约1.9%的95%风险上界（3/n近似），不能宣称总体零幻觉。图像不清晰时允许unknown，但单独报覆盖率。
- 时间段：只对人工匹配到的动作事件计算开始/结束边界误差中位数、P90和区间IoU；事件漏检仍计入动作recall。1fps暂定误差中位数≤1秒、P90≤2秒；该值不是帧级剪辑精度承诺。

诊断指标：有效schema比例、HTTP成功率、429/超时/截断率、P50/P95响应时延、端到端耗时、可辨文字字符错误率（不可辨文字报N/A，另计凭空OCR）、重复标注一致性。延迟只看10个样本不报稳定P95。

失败处理：不在主测试偷偷补调以掩盖失败。另做显式、限次重试，保留第一次结果与实际成本；超时可能已计费，usage缺失计为费用未知并对账，不能记0元。无权限/型号不支持视频应报告不可评测，不计为视觉理解差。

160条同一样本配对比较候选；报告按拍摄批次分组bootstrap置信区间（固定种子），错误类型按场景列出。差异很小时扩大样本，不能把1～2条的领先当成明确胜出。难例配额与自然分布不同，结果仅适用于此样本框架。

## 7. 分阶段执行与模型选择规则

A. 接口小测：5条开发样本×5候选=25次，验证账号开通、视频输入、结构化格式、usage和截断。2.0 Pro仅在仍可调用且有比较价值时加测，不列入默认生产候选。
B. 开发筛选：40条×5候选=200次。盲评后保留两个；20条×2候选×2额外配置=80次用于fps/分辨率消融。先确定共同配置；若比较各自最佳配置，单列“生产方案对比”，不混为模型单变量比较。
C. 冻结验收：160条×2候选=320次；同一批次不再修改提示词/词表。另20条×2候选×2追加重复=80次。上限计划共705次（不含额外历史模型、重试、复核），阶段已有可完全复用的请求应去重，不为凑次数重复付费。
D. 检索验收：先用100～200条已分析样本建立临时检索索引，固定同一embedding/检索设置，人工设计30～50条真实镜头需求和相关素材集合，至少10条无匹配需求，报告Precision@5和有匹配查询的Hit@5、无匹配误报率。不能用当前没有实现的检索结果当P1分数；这是P1到P2的附加验收。

选择规则：
- 2.0 Mini若满足质量门槛，且配对差异在预先约定的2个百分点容忍范围内、置信区间足够窄，可作为简单标签默认；不达标不因便宜放行。
- 详细描述/动作入库优先验证2.1 Lite；若2.0 Lite在同口径下质量相近且实际可用成本更低，可选旧Lite，但考虑生命周期。
- 2.1 Pro用于难例、争议审核与时间关系要求高的素材；只有质量增益显著抵消费用/时延，才全量默认。
- Turbo必须证明确有吞吐/延迟或质量收益；名字含Turbo不代表比Lite便宜，未测前不作快或准的断言。
- 分层路由不是“Mini+随意抽一点Pro就可靠”：以缺字段、动作/时间矛盾、unknown过多等可解释信号路由，并随机抽查已通过样本；模型自报confidence不能单独决定放行。测路由召回率、升级率和最终可用成本，再决定是否值得复杂化。

## 8. 工程接入差距与数据生命周期

当前程序已有单模型视频压缩、描述校验和成功缓存，但尚无多模型评测器、失败请求账本、预算阈值、盲评分导入、重复请求绕过缓存与显式thinking/service_tier控制。现有缓存键还需增加服务档位、思考策略、温度、输出上限、评测run/repeat标识，且区分冷调用和缓存。

下一步先补评测命令及上述日志/配置，不要直接用当前CLI连续调用来宣称公平评测。本方案不是已实现的评测器，也没有自动修改本地API Key配置或发起模型调用。

NAS严格只读，源仅在抖音自播；按2MiB/s顺序复制选中样本到本地，每次只暂存一条。为公平比较同一代理可跨当前样本的多个模型请求暂留；该样本全部模型/消融处理完即删除本地原片副本和代理，失败也清理；持久保存指纹、标注、输出与账本。缓存命中时复用结果但不参与真实延迟统计。原片永不删除或改名。
